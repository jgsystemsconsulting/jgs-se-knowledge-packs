# Chapter: Technical Reviews and Audits

## Core Idea

A tailored series of technical reviews and audits gives the program defined points to judge achievement, technical maturity, and risk. Reviews are event-driven controls, not calendar ceremonies. The PM, systems engineer, and software engineer jointly set success criteria so each event supports knowledge-based acquisition decisions.

## Frameworks Introduced

- **Event-driven technical review and audit sequence** across the Major Capability Acquisition life cycle.
- **Entrance and exit logic** as method: define what must be ready to start, and what evidence closes the event.
- **Named events:** ASR, SRR, SFR, PDR, CDR, SVR/FCA, PRR, PCA.
- **Roles and responsibilities** for government and contractor participants at each event.
- **Agile-aware review practice** so iterative development still faces technical baseline questions.

## Key Concepts

- **Why reviews exist.** They evaluate significant achievements and assess maturity and risk so the program can proceed, replan, or stop with evidence.
- **Pathway alignment.** Under DoDI 5000.02, the AAFDID tool surfaces statutory and regulatory document needs. Regardless of pathway, align applicable technical reviews to decision points and strip non-value events.
- **Success criteria ownership.** The PM and technical leads define entrance criteria (work and products ready) and exit criteria (evidence the event objectives were met). Criteria are program-specific; this pack does not reproduce criteria tables cell by cell.
- **ASR (Alternative Systems Review).** Confirms preferred concept framing and readiness to proceed into requirements-focused work.
- **SRR (System Requirements Review).** Confirms system requirements are understood, consistent, and ready to drive design.
- **SFR (System Functional Review).** Confirms functional baseline readiness before preliminary design solidifies.
- **PDR (Preliminary Design Review).** Confirms preliminary design and allocated baseline maturity for the next design wave.
- **CDR (Critical Design Review).** Confirms detailed design readiness to build and verify the product baseline path.
- **SVR/FCA (System Verification Review / Functional Configuration Audit).** Confirms the system was built to the functional requirements and verification evidence is complete enough for the decision at hand.
- **PRR (Production Readiness Review).** Confirms manufacturing and quality readiness before production commitment.
- **PCA (Physical Configuration Audit).** Confirms the as-built configuration matches the product baseline.
- **Process view.** A generic technical review process prepares, conducts, and closes each event with action tracking. Agile programs still map iteration evidence into these baseline questions.

## Mental Models

- **Knowledge gate, not date gate.** Hold the review when entrance evidence exists.
- **Criteria before slideware.** Write entrance and exit logic first; charts second.
- **Audit closes the loop.** Reviews look forward; audits confirm what was built or configured.
- **Agile still baselines.** Iterations produce evidence; events still answer maturity questions.

## Key Takeaways

- Plan a tailored review and audit set tied to pathway decisions and risk.
- Define entrance and exit logic with the PM and technical leads; do not copy generic tables blindly.
- Use the named event sequence (ASR through PCA) as the vocabulary, then scale.
- Keep roles clear so government and contractor preparation is not ambiguous.
- Fold agile iteration evidence into the same baseline questions.

## Anti-patterns

- Calendar-driven reviews held without entrance evidence.
- Criteria tables copied without tailoring to the system's risk and pathway.
- Treating Agile delivery as a reason to skip baseline confirmation events.
