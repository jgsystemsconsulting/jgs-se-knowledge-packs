# Chapter 8: Software Function Scope and Off-the-Shelf Software

Sources: S8 Off-The-Shelf Software Use in Medical Devices (2023-08-11), §§ I–IV and Appendix A (OTS definition and documentation elements, risk assessment, V&V testing, development-methodology and maintenance assurance, marketing-application notes, maintenance and obsolescence); S10 Medical Device Data Systems, Medical Image Storage Devices, and Medical Image Communications Devices (2022-09-28), §§ III–IV (Non-Device-MDDS vs Device-MDDS definitions and policy, active patient monitoring, multi-function products).

## Core Idea

Two different scope questions sit in this chapter. First: is a data-handling software function a device at all? S10 answers with the Cures Act carve-out for Non-Device-MDDS (and related medical image storage/communications software): solely transfer, store, convert formats, or display medical device data and results, without analysis, interpretation, or control of connected devices. Hardware that does the same jobs stays inside the device definition, with a separate enforcement-discretion policy. Second: when off-the-shelf (OTS) software sits inside a regulated device, whose life-cycle control is missing and who still owns safety? S8 answers that the manufacturer generally gives up complete software life-cycle control of the OTS component but keeps responsibility for continued safe and effective device performance. Documentation Level (Basic or Enhanced) from S1 scales what OTS evidence goes in the premarket file. Clinical decision support is not here; that boundary is ch11.

## Frameworks Introduced

- **Non-Device-MDDS vs Device-MDDS (S10)**: software solely intended to transfer, store, convert formats, or display medical device data and results is not a device under section 201(h); hardware with the same sole intents remains a device (Device-MDDS), subject to FDA's stated non-enforcement posture when limited to assisting those software functions.
- **OTS software (S8)**: a generally available software component used by a medical device manufacturer for which the manufacturer cannot claim complete software life cycle control (examples: operating system, printer/display libraries). Industry often labels similar components SOUP; this pack's FDA source vocabulary is OTS.
- **OTS documentation elements × Documentation Level (Table 1)**: Description of OTS Software; Risk Assessment of OTS Software; Software Testing as part of Verification and Validation; Assurance of Development Methodologies and Continued Maintenance of OTS Software (Enhanced submission depth; Basic keeps methodology/maintenance evidence in the DHF unless FDA asks).
- **Maintenance and obsolescence concerns (Appendix A)**: safety, design, V&V/regression, installation, obsolescence, and product configuration when OTS components change under a product baseline the manufacturer does not fully control.

## Key Concepts

- **Non-Device-MDDS boundary.** Software functions solely intended to transfer, store, convert formats, or display medical device data and results (including medical images, waveforms, signals, or other clinical information) are not devices and are not subject to device regulatory requirements. They must not modify the data, control functions or parameters of connected medical devices, or analyze or interpret data. Analyze/interpret examples that stay devices include alarms, alerts, or prioritization on multi-patient displays typically used for active patient monitoring.
- **Active patient monitoring is not a free pass into Non-Device-MDDS.** Non-Device-MDDS may transfer/store/convert/display data that may or may not be intended for active patient monitoring. Device functions intended for active patient monitoring to enable immediate awareness for potential clinical intervention show timely-response clinical context (e.g., in-hospital monitoring) or clinical condition (e.g., life-threatening arrhythmia detection, time-sensitive diabetes intervention). Nurse telemetry secondary-alarm stations and home caregiver alert paths that drive immediate clinical action are device examples; remote display of glucose values the user can independently review without immediate-action intent can stay Non-Device-MDDS.
- **Device-MDDS hardware policy.** Hardware solely intended to transfer, store, convert formats, or display medical device data and results remains a device. FDA does not intend to enforce FD&C Act requirements for such hardware when limited to assisting those software functions and when the hardware does not modify data or control connected devices. Covered regulation examples include 21 CFR 880.6310 (MDDS), 892.2010 (medical image storage), and 892.2020 (medical image communications). Specialized medical display hardware (e.g., digital mammography/radiology/pathology/ophthalmology displays, integral 3D robotic or ICU bedside displays) is not treated as MDDS/image storage/communications Device-MDDS and is not excluded by the Cures Act on that path. General-purpose IT infrastructure (routers, NAS, generic monitors, ordinary PDF tools) intended only for ordinary data jobs is not a device function for software or hardware.
- **Multi-function products with MDDS.** Consistent with section 520(o)(2), FDA does not regulate Non-Device-MDDS functions inside a multi-function product as devices. Device-MDDS hardware functions currently sit under the same non-enforcement posture described above. FDA may still assess how Non-Device-MDDS or Device-MDDS functions affect safety and effectiveness of the product's device function(s); see the Multiple Function Device Products guidance for the product-level frame (ch01 routes the pathway question).
- **OTS definition and manufacturer duty.** OTS is generally available software the manufacturer uses without complete life-cycle control. Premarket submissions in S8's scope include 510(k), De Novo, PMA, IDE, and HDE. Multi-function products with "other functions" also pull the Multiple Function Device Products recommendations when building the software file.
- **Description of OTS software (both levels).** For each OTS component: title and manufacturer; version, release date, patch, upgrade designation; end-user OTS documentation; why the OTS is appropriate; expected design limitations; computer system specifications (hardware and software, including exact OS/driver/utility versions and patches); end-user install/configure rights and forbidden non-specified software; what the OTS does in the device and links to other software (including outside the device); how the sponsor knows it works (testing commensurate with Documentation Level, results, defect/update access); how configuration is controlled (version checks, storage, installation, maintenance support). Use OTS only as specified in design documentation; version changes update that documentation.
- **Risk assessment of OTS software.** Both Basic and Enhanced submissions carry a risk management file (plan, assessment showing OTS-related risks are appropriately mitigated, report). OTS function risks used in the device belong in that file; residual-risk evaluation method should be clear in the plan.
- **V&V testing of OTS software.** Include test plans and results. Testing covers OTS-developer work and sponsor qualification of the OTS for the specific device use. Plans should name exact OTS title and version; integrate and test with that OTS. Results scale with Documentation Level and with hazards in the risk file. Multiple allowed OTS versions mean validation for each version. Provide a current list of OTS software defects (pair with unresolved-anomaly expectations in ch02).
- **Development methodologies and continued maintenance (Enhanced submission depth).** Provide assurance that the OTS developer's product development methodologies are appropriate and sufficient for the intended use in the device (for example by reviewing design and development methodologies and qualification documentation). Demonstrate mechanisms for continued performance, maintenance, and support if the OTS developer changes the software or ends support. If that assurance is impossible and residual risk after controls is unacceptable under the risk plan, the OTS may not be appropriate. For Basic, keep this evidence in the DHF; FDA may still request it in review.
- **Marketing-application notes (Section IV).** OTS vendors may place proprietary development/validation detail in a Master File for Devices. Whether an OTS change needs a new 510(k) follows the same change guidances as other software (ch10). IDE and PMA criteria do not loosen because OTS is present; PMA depth for OTS life-cycle assurance tracks overall device risk, OTS role, and probable risk of death or serious injury from OTS failure or flaw. Labeling should specify allowed OTS versions (unless embedded and user-immutable), warn against non-specified software, state minimum validated hardware platforms, and describe user installation checks.
- **Maintenance and obsolescence (Appendix A).** New or modified OTS under a baseline can break structural integrity the manufacturer never fully controlled. Address safety impact and hazard traceability (including release bulletins, manuals, patches, and field experience searches); design impacts (resources, timing, memory organization, human factors, data integrity, build tools); full-system regression, not only black-box claims; field installation impact; obsolescence (continued availability, retirement plan, replacement of fielded components); and explicit product configuration (hardware platform, software platform, other OTS, internal applications). Operating systems, drivers, utilities, and networks get extra scrutiny because general-purpose OTS often carries unused complexity and weaker error tolerance than device use needs; networked devices need defined speed, architecture, NOS trade-offs, data integrity, and management/security requirements.

## Mental Models

- **Scope first, then ownership.** Ask "is this function a device?" (MDDS/CDS carve-outs) before "whose code is it?" (OTS inside a device function).
- **Solely is doing real work.** Transfer/store/convert/display alone can exit the device definition; add analysis, interpretation, control, alarms for immediate intervention, or active-monitoring device characteristics and the exit closes.
- **Hardware MDDS ≠ software MDDS.** Software Non-Device-MDDS is out of the device definition; hardware Device-MDDS stays in, with enforcement discretion when narrowly assisting the software jobs.
- **OTS transfers control, not responsibility.** The invoice does not move design-control or safety ownership. Documentation Level sets submission minimums; the quality system still holds the file.
- **Black-box comfort is not system assurance.** Unknown OTS logic paths force sponsor qualification, defect tracking, regression, and a maintenance/obsolescence plan that survives vendor churn.

## Anti-patterns

- **Calling any data pipe "MDDS" while it analyzes, prioritizes, alarms, or controls a connected device.** Those are device software functions.
- **Treating active patient monitoring display paths as Non-Device-MDDS by default.** Immediate-awareness clinical context or condition keeps them in device territory.
- **Assuming specialized medical displays are Device-MDDS under enforcement discretion.** S10 keeps them outside that MDDS bucket.
- **Shipping OTS on vendor marketing claims without sponsor risk file, version-pinned tests, and defect list.** S8 expects manufacturer qualification evidence.
- **Skipping Enhanced methodology/maintenance assurance because "it's just an OS."** When Documentation Level is Enhanced, continued support and developer-methodology assurance are submission content.
- **Ignoring obsolescence until the vendor ends support.** Fielded devices still need a support path; plan retirement and replacement before the cliff.
- **Mixing CDS analysis into this chapter's MDDS test.** CDS uses section 520(o)(1)(E) and lives in ch11.

## Key Takeaways

1. Non-Device-MDDS software (solely transfer/store/convert/display of medical device data and results, no analysis/interpretation/control) is not a device under section 201(h).
2. Alarms, alerts, prioritization, and active patient monitoring paths aimed at immediate clinical intervention are device software functions, not Non-Device-MDDS.
3. Device-MDDS hardware remains a device; FDA states non-enforcement when hardware only assists the transfer/store/convert/display software functions and does not modify data or control connected devices.
4. Multi-function products keep Non-Device-MDDS out of device regulation for those functions, but impact on device functions can still be assessed.
5. OTS is generally available software without complete manufacturer life-cycle control; the manufacturer still owns safe and effective device performance.
6. OTS premarket content is Description, Risk Assessment, and V&V testing at both Documentation Levels; development-methodology and continued-maintenance assurance is Enhanced submission depth (Basic retains it in the DHF).
7. Pin exact OTS versions in design and test evidence; validate each allowed version; track defects; control configuration against incorrect loads.
8. Maintenance of OTS under a baseline needs safety, design, full regression, installation, obsolescence, and configuration analysis because the sponsor lacks full OTS life-cycle control.
9. OTS changes still run through the ordinary 510(k)/IDE/PMA change and evidence rules; labeling should lock allowed versions and platforms for user-selectable software.
10. CDS device/non-device criteria are ch11; this chapter stops at MDDS scope and OTS inside regulated device software.
