# Glossary: faa-8110-49

Terms as the pinned FAA sources use them, with the chapters that carry the detail. FAA meaning first; retired taxonomies are named only as retired.

- **AC (Advisory Circular)**: FAA guidance that is an acceptable means, not the only means and not a regulation. AC 20-115D and AC 20-152A are the recognition instruments for airborne software and airborne electronic hardware: each names the RTCA/EUROCAE document it accepts and adds FAA-specific objectives or transition rules. → ch01, ch05, ch07
- **AC 00-69**: Best practices for airborne software development assurance (2017-07-21). In this pack: change impact analysis, data and control coupling, design-level error handling. Best practices, not guidance, not a means of compliance. → ch11, ch12, ch13
- **AC 00-72**: Best-practice companion AC for DO-254 users, also cited for electronic component management and DAL D help. Named but not packed. → ch01, ch07, ch10
- **AEH (airborne electronic hardware)**: Electronic hardware intended to be installed in airborne equipment or systems. AC 20-152A applies to AEH contributing to hardware DAL A, B, or C; DAL D is outside its required use. → ch01, ch07
- **ASE (Aviation Safety Engineer)**: The FAA specialist who, for conformity, establishes the software baseline and test-configuration facts and initiates Form 8120-10 (the expansion is the Order 8110.49A acronym table's; ch04 describes the role). → ch04
- **ASI (Aviation Safety Inspector)**: The MIDO/MISO manufacturing inspector who executes the conformity tasks listed on Form 8120-10: witnessing builds and loads, verifying part and version numbers, and recording installation conformity. MIDO and MISO are the Manufacturing Inspection District and Satellite Offices. → ch04
- **CBA (circuit board assembly)**: A board, or collection of boards, contributing to hardware DAL A/B/C that hosts complex custom or complex COTS devices. CBA-1 requires board-level requirements capture, validation, verification, configuration management, and flow-down so the CBA performs its intended function. → ch10
- **Change impact analysis (CIA)**: The analysis run when legacy software is modified, establishing the extent and impact of changes and the verification they require, with results summarized in the PSAC or SAS. AC 00-69 section 3.1 gives the best-practice contents. → ch05, ch06, ch11
- **Certification basis**: The regulations, and accepted means of complying with them, that a project is judged against. Reviews give timely technical interpretation of it, and conformity shows the article matches approved type design under 14 CFR 21.33(b). → ch02, ch04
- **Certification credit**: Regulatory recognition of a system certification test run under an FAA-approved test plan to show compliance. That approved test plan is not the DO-178B Software Verification Plan. → ch04
- **Certification liaison**: The communication process between applicant and authority described in DO-178B/C Section 9, which Order 8110.49A Chapter 2 operationalizes for FAA staff through desk and on-site reviews. → ch02, ch05, ch06
- **Conformity inspection**: The documented checkpoint confirming software matches approved type design, in two forms: software part conformity (each test for certification credit) and software installation conformity (aircraft-level ground or certification flight tests). Part conformity must succeed before installation conformity is requested. → ch04
- **COTS device**: A packaged semiconductor device (integrated circuit or multi-chip module) developed by a supplier for a wide range of customers, with design and configuration controlled by the supplier rather than the aviation applicant. Section 6 objectives (COTS-1 through COTS-8) apply after a complexity assessment classifies the device as complex. → ch10
- **COTS IP**: Commercially available design functions (modules, blocks, IP libraries) instantiated inside a custom device, in Soft (RTL), Firm (netlist), or Hard (physical layout) form. Manufacturer-embedded Hard IP in FPGA/PLD silicon is instead treated as part of a COTS device under section 6. → ch09, ch10
- **Critical configuration settings**: Settings the applicant deems necessary for proper hardware usage which, if inadvertently altered, could change COTS device behavior so the device no longer fulfills its intended function. COTS-8 requires mitigation at hardware, software, or system level for complex COTS in DAL A/B functions. → ch10
- **Custom device**: A PLD, FPGA, or ASIC: ED-80/DO-254's custom micro-coded components, developed for the application. → ch07
- **DAL (development assurance level)**: The assurance level a system safety assessment assigns from failure-condition severity: software level for software, hardware DAL for AEH. CD-1 records the level of each custom device in the PHAC, and AC 20-152A use is required only at hardware DAL A, B, and C. → ch03, ch06, ch07
- **Data coupling / control coupling**: Distinct analyses, both required. Specifying interfaces and dependencies in the design phase supports the verification objective. DO-248C FAQ #67 named only. → ch12
- **Design-level error handling**: Foreseeable error sources mitigated in requirements, with runtime protection named for software levels A and B. DO-333 named only. → ch13
- **Designee (and the software DER)**: A person the FAA authorizes to exercise delegated authority: reviews may be delegated to designees, designee capacity scores into LOI, and a delegated software DER may approve the software baseline on Form 8110-3. → ch02, ch03, ch04
- **Desk review / on-site review**: The two valid review forms: desk review examines life cycle data remotely; on-site review adds access to software personnel, automation, and the test setup under nine agreed arrangements. Either may be delegated to authorized designees. → ch02
- **DO-178B / ED-12B**: The prior generation airborne software standard. AC 20-115D lets mature DO-178B process users keep those processes for new development only when all six section 5 criteria hold, and the legacy flows of section 9 build on DO-178B baselines. → ch05, ch06
- **DO-178C / ED-12C**: The recognized airborne software standard, applied together with its supplements and DO-330 wherever AC 20-115D says DO-178C. The AC points at the standard's objectives and Annex tables without restating them; this pack names software levels A-D as the order's worksheets and the AC use them. → ch01, ch03, ch05
- **DO-254 / ED-80**: The recognized airborne electronic hardware standard, treated by AC 20-152A as the industry standard for complex custom device development assurance, with the AC adding objectives and clarifications in its sections 5.5 through 5.11. → ch07
- **ECM (electronic component management)**: The process covering COTS device selection, qualification, configuration management, and access to datasheets, errata, and manufacturer change information. COTS-2 requires it, with added maturity attention at DAL A/B. → ch10
- **FAA Form 8110-1**: The TIA form used for aircraft-level testing; it carries the software part and version number under request and the ASI verification actions when installation conformity is performed. → ch04
- **FAA Form 8110-3**: A designee's Statement of Compliance with the Federal Aviation Regulations; the alternate path for approving a software baseline for FAA testing, stating that purpose explicitly. → ch04
- **FAA Form 8120-10**: The Request for Conformity the ASE initiates so the ASI can witness or verify build, load, integrity-check, and test-setup steps. → ch04
- **FLS (field-loadable software)**: Software loaded into equipment in the field, needing four AC-level add-ons: developer support data, corruption and partial-load protection at the software level, a verifiable loaded part number, and inhibit of field loading in flight or other safety-critical phases. → ch06
- **HDL code coverage**: A recognized elemental-analysis method for digital devices when run during requirements-based verification; it shows which HDL elements the simulations exercised, not whether requirements testing is complete. CD-9 requires planned coverage criteria and justified holes at DAL A/B. → ch08, ch09
- **HCI / HECI**: The Hardware Configuration Index completely identifies hardware configuration, embedded logic, and development life cycle data. The Top-Level Drawing corresponds to an HCI and includes the life cycle environment or refers to a Hardware Environment Configuration Index (HECI), supporting consistent replication. → ch08
- **Legacy software**: Previously approved software, or a component of it, used under DO-178, DO-178A, or DO-178B as the means of compliance; modification or reuse follows the Figure 1 flow in AC 20-115D section 9. → ch06
- **Legacy software levels (retired taxonomies)**: DO-178's Critical / Essential / Non-Essential ratings and DO-178A's numeric levels 1-3 survive only as inputs to the Table 1 acceptability mapping, which decides whether a legacy level satisfies the newly assigned level. They are named only as retired. → ch06
- **LOI (level of FAA involvement)**: How much certification-authority attention a software project receives, determined and documented as early as practicable. Worksheet 1 bands by software level (D LOW; C LOW or MEDIUM; A and B MEDIUM or HIGH), Worksheet 2 scores experience, capability, service history, application attributes, and designee capacity into a Total Score Result (TSR), and Worksheet 3 combines TSR with software level into LOW / MEDIUM / HIGH. The worksheets are examples, not mandates. → ch02, ch03
- **LRU (Line Replaceable Unit)**: The equipment into which the conformity-checked software test configuration is installed, and whose part and version numbers the ASI verifies. → ch04
- **Microcode**: Hardware-level instructions inside some COTS devices. It counts as part of the qualified device only when manufacturer-delivered, under the manufacturer's configuration management, and qualified together with the device; otherwise COTS-4 requires a means of compliance and a PHAC pointer. → ch10
- **OPR (open problem report)**: A problem report whose unresolved state can leave DO-178B objectives unsatisfied. Open process-related OPRs, with audits and review findings, block the DO-178B process reuse path and gate legacy reuse until resolved or planned. → ch05, ch06
- **Order 8110.49A**: The FAA's internal software approval guidelines: how AIR offices and designees run software reviews (chapter 2), involvement sizing (chapter 2 and Appendix A), and conformity inspection (chapter 4) on DO-178B/C projects. It binds FAA staff, not applicants, and cancels and supersedes Order 8110.49 Chg 2, whose deleted chapters 5-16 are named only as retired. → ch01, ch02, ch03, ch04
- **PDI (Parameter Data Item)**: Configuration data with its own transition criteria: existing PDI processes must have been FAA-accepted on a previous certified project, or new PDI processes must be established per DO-178C, both in the section 5 reuse test and in the legacy flow. → ch05, ch06
- **PDH (previously developed hardware)**: A custom-developed hardware device already installed in an airborne system or equipment approved through FAA TC/STC or authorized through TSOA. Reuse runs through ED-80/DO-254 section 11.1: modification, a change of function, use, or a higher failure condition classification, or a design-environment change can each invalidate prior credit (CD-12). → ch08
- **PHAC (Plan for Hardware Aspects of Certification)**: The planning document, or related plans, recording how AC 20-152A objectives will be met: DAL and simple/complex classification with justification, the COTS IP approach, complexity calls, microcode pointers, and PDH assessments. It is submitted for certification. → ch07, ch08, ch09, ch10
- **PSAC (Plan for Software Aspects of Certification)**: The software planning document that, when supplements are used, describes how DO-178C and each supplement apply together and which objectives apply to which software components, and that summarizes CIA results for legacy modifications. → ch05, ch06
- **Recognition chain**: How FAA guidance points at industry standards: an AC names an equivalent EUROCAE ED / RTCA DO pair, and the applicant satisfies that document's objectives, activities, and evidence plus any AC additions. The AC does not reprint the standard. → ch01, ch05, ch07
- **Robustness**: The expected behavior of a design under abnormal and boundary (worst-case) operating conditions. CD-8 requires DAL A/B hardware to define those conditions and their expected behaviors as requirements, often as derived requirements. → ch08
- **SAS (Software Accomplishment Summary)**: Part of the DO-178B Section 9.4 type design data set and of the conformity baseline; also where legacy change impact analysis results are summarized. → ch04, ch06
- **SCI (Software Configuration Index)**: The configuration record identifying the software under configuration control. Installation conformity requires the requested part and version to be identifiable, reproducible, and documented in the SCI or similar record. → ch04, ch08
- **SEE (Single Event Effects)**: Susceptibility assessment that AC 20-152A explicitly does not address, though the PHAC may still record SEE certification considerations. → ch01, ch07
- **Simple / complex custom device**: A device is simple only when a technical assessment shows it can be comprehensively verified by deterministic tests and analyses under all foreseeable operating conditions with no anomalous behavior; CD-1 records the call and the justification. Otherwise it is complex and takes full ED-80/DO-254 plus AC sections 5.5 through 5.11. An assembly of only simple items may itself be complex. → ch07
- **Supplement (DO-330, DO-331, DO-332, DO-333)**: The ED-215 to ED-218 companions recognized with DO-178C for tool qualification, model-based development, object-oriented technology, and formal methods. Supplements apply when those techniques are used, are never stand-alone means, and the PSAC must describe the combined objective coverage. → ch05, ch06
- **TC / STC / ATC / ASTC / TSOA**: The project types Order 8110.49A covers: Type Certificate, Supplemental Type Certificate, Amended Type Certificate, Amended Supplemental Type Certificate, and TSO authorization. → ch01, ch04, ch05
- **TIA (Type Inspection Authorization)**: The FAA aircraft-level inspection programme whose ground or certification flight tests trigger software installation conformity. → ch04
- **Tool assessment and qualification (AEH)**: The ED-80/DO-254 Figure 11-1 walk clarified by AC 20-152A section 5.8: tool identification with environment and revision, independent output assessment (CD-10), relevant-history data (CD-11), and the rule that design-tool history is never a stand-alone qualification means. → ch08
- **Tool qualification (software)**: Transitioned to DO-330 by AC 20-115D section 10: new or modified legacy tools derive a TQL from the assigned software level, with Table 2 correlating DO-178B tool types to DO-178C tool criteria. Development tools keep DO-178B processes only where the prior level meets the required TQL, and TQL-4 verification tools requalify under DO-330. → ch05
- **TSR (Total Score Result)**: The Worksheet 2 score that Worksheet 3 combines with software level to land inside the level's LOW / MEDIUM / HIGH band; higher scores push involvement down within the band. → ch03
- **Type design**: The approved configuration data that conformity checks against. For software it is at minimum the DO-178B Section 9.4 set: Software Requirements Data, Design Description, Source Code, Executable Object Code, the SCI, and the SAS; at Level D, Design Description and Source Code drop out. → ch04, ch05
- **UMS (user-modifiable software)**: Software whose modifiable portion can be changed by the equipment user. The AC add-on requires that portion to be developed at a software level at least as high as the level assigned to that software. → ch06
