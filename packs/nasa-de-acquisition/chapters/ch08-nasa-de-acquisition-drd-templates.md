# Chapter: DRD template library

## Core Idea

Appendix B is a library of Data Requirements Description (DRD) templates and instructions. A DRD defines a data deliverable the same way a drawing defines a part: purpose, contents, format, timing, and control level. Programs select and tailor templates; they do not treat the appendix as a mandatory full suite. This pack describes the library method. It does not copy template fields, option worksheets, or list rows cell by cell.

## Frameworks Introduced

- **DRD as data-contract interface.** Each DRD pins what is delivered, how it is encoded, when it is due relative to milestones, and how strongly the Government controls it.
- **Template library, not fixed suite.** Baseline-era pack identity listed a long fixed suite. Revision A keeps a template library idea: choose the classes the program needs, tailor them, and add program-unique DRDs when gaps remain.
- **Instructions before forms.** Appendix B explains DRD purpose and section roles so tailoring is intentional.
- **Option worksheets where needed.** Some classes (for example technical data package options referencing MIL-STD-31000C concepts) use worksheets to record tailoring choices without pasting the external standard.

## Key Concepts

- **Section roles (described, not copied).** Typical DRD anatomy includes identification, purpose, contents/scope of the data item, format and named neutral encodings where required, submission timing tied to events not naked calendar dates, and access or Data Type style control.
- **Data Type control idea.** Control intensity ranges from strong approval-before-use patterns through inspection-only patterns. Pick the lowest level that still protects the baseline and the digital thread.
- **Configuration and data management companions.** Templates related to configuration and data management planning, status accounting, audits, and change artifacts exist so CDM SOW language has matching data items.
- **Model and definition classes.** Templates covering model-based definition, CAD-related packages, requirements exchange concepts, and master index style deliveries appear as library members when the program's digital thread needs them. Names come from the re-fetched appendix, not from a frozen baseline roster.
- **Tailoring rules.** Strike what does not apply; add program-unique content; keep references to external standards as names and version pins, never as pasted standard text.
- **Legal and procurement review.** Example DRDs are starters. Binding use needs program, procurement, and legal review.

## Mental Models

- **Library shelf.** Walking out with every book is not a success metric; walking out with the right set is.
- **DRD before shall.** SOW shall-statements that point at empty DRDs create disputes.
- **Format is content.** A contents section without a format section invites proprietary lock-in.

## Anti-patterns

- Copying every template field into the pack or into a contract without tailoring.
- Keeping a baseline "full suite" identity when the program only needs a slice.
- Pointing at an external standard name without a DRD that states which options apply.
- Using calendar dates instead of milestone-relative timing for data events.

## Key Takeaways

- Appendix B is a DRD template library with purpose and section instructions.
- Select, tailor, and review; do not mandate the whole shelf.
- DRDs define contents, format, timing, and control for each data item.
- External standards stay named, not quoted.
- No template fields or worksheets are copied into this pack.
