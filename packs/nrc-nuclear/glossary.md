# Glossary: nrc-nuclear

Terms as the pinned NRC sources and the chapters use them, with the chapters that carry the detail. Endorsed IEEE, IEC, and IAEA standards appear as designations only; their text lives with the owners.

- **anomaly**: A reported deviation of software or documentation from expected behavior. Anomaly reports are generated and disseminated in V&V work, feed the corrective-action path that ends in a verified change release, drive retest until resolution, and stay under configuration control. (ch02, ch04, ch05, ch06, ch07)
- **audit**: An examination that safety-related activities were performed correctly. Functional, in-process, and physical software audits are part of the minimum V&V set, with IEEE Std 1028-2008 the acceptable method; configuration audits sit inside CM, and B.4 audits a sample of implementation documentation. (ch01, ch04, ch05, ch07)
- **baseline**: Meaning (1) of the endorsed standards' glossaries: a specification or product formally reviewed and approved by responsible management, thereafter under change control. SCM control points map to baselines, and approval authority scales with life cycle stage and safety importance. (ch03, ch04, ch07)
- **BTP (Branch Technical Position)**: Staff review guidance inside SRP Chapter 7. BTP 7-14 Rev 6 carries the review method and acceptance criteria for digital computer software in safety systems: acceptable plans, evidence the plans were followed, and acceptable design outputs. (ch01, ch07)
- **CL (code listings)**: Design output carrying the implemented code, scored on functional and process characteristics. Comments and annotations must make developer intent clear to the reviewer and to future modification; undocumented code is not suitable for safety-related nuclear use. (ch07)
- **configuration item**: Any software work product placed under configuration control, far beyond delivered code: requirements, designs, code, data files, exact support-software versions, safety-essential libraries, quality-affecting plans, test artifacts and qualifying results, documentation, test cases, databases and configuration data, change documentation, and production tools such as compilers. (ch03, ch04)
- **configuration status accounting**: The CM function that answers "what is current": item identifications, baselines, problem-report status, change history, and release status, documented before an activity group completes. (ch04, ch07)
- **design output**: Documents that define technical requirements of the end product installed in the plant: the SRS, software design specification, hardware and software architecture designs, code listings, system build documents, installation configuration tables, and operations, maintenance, and training manuals. (ch01, ch07)
- **ICT (installation configuration tables)**: Design output recording the plant-specific configuration, options, variable setpoints, and operating methods of the installed system; each installed program element traces back to the integrated software elements that created it. (ch07)
- **independent V&V**: V&V performed with technical, financial, and managerial independence from the development effort. A separate company is not required, but Criteria I and III substance is; the licensee retains ultimate responsibility even when an external organization performed V&V, and verifiers match or exceed designer proficiency. (ch05, ch07)
- **integrity level**: The four-level scheme (level 4 highest, level 1 lowest) of IEEE Std 1012-2004 and IEEE Std 829-2008 that sets minimum V&V and test-documentation tasks. Safety system software is integrity level 4 or the equivalent by mapping; likelihood-based downgrades are rejected. (ch05, ch06)
- **ML accession**: The ADAMS document number NRC assigns each source (for example ML16019A308 for BTP 7-14 Rev 6); carried in every chapter's Sources line. (ch01-ch08)
- **OM (operations manual)**: Design output scored on process characteristics only, since it imposes no requirements on the software. Completeness emphasizes unusual and emergency operation, error recovery and backup, and descriptions of code-generated error messages. (ch07)
- **RG (Regulatory Guide)**: An NRC document describing a method the staff considers acceptable for meeting the regulations. Following a guide is voluntary; an applicant may propose an alternative with adequate demonstration. The July 2013 family RG 1.168 through 1.173 partitions the software life cycle. (ch01)
- **SAD (software architecture description)**: Required design output, reviewed with the hardware architecture. It must let the reviewer understand how the software works, its data flow, and its deterministic nature, with modular design that controls error propagation and safety functions separated from normal operating functions. (ch07)
- **safety system**: The plant instrumentation and control whose digital software must be designed, fabricated, installed, and tested to quality standards commensurate with safety importance, under the 10 CFR 50.55a(h) path that names IEEE Std 603-1991. (ch01)
- **SBD (system build document)**: Design output proving the delivered and installed software is the tested and V&V'd build; it records the correct versions, revisions, and dates of all required software elements, including library units actually used. (ch07)
- **SCM (software configuration management)**: Identification, control, status accounting, and audit of software items across the life cycle. The SCMP covers designs, code, interfaces, documentation, vendors, qualification information, and build/release/delivery, with a software librarian owning versions. (ch03, ch04, ch07)
- **SDOE (secure development and operational environment)**: The security posture the sources point to RG 1.152 for: controls against inadvertent or unauthorized modification, undocumented code, and unneeded functionality, carried through planning security, V&V secure analysis, CM controls, and the design-output security characteristic. (ch01, ch02, ch04, ch05, ch07)
- **SDS (software design specification)**: Required detailed-design design output: equations, algorithms, control logic, and data structures specified fully enough to code, with deterministic timing and behavior under unexpected, incorrect, or improper input, hardware, or software behavior. (ch07)
- **SIntP (software integration plan)**: Planning document covering software, hardware/software, and multi-vendor integration, with documented integration tests and expected results and integration tools qualified to the safety significance of the software. (ch02)
- **SInstP (software installation plan)**: Planning document covering installation procedures and functional checks, anomaly reporting to the developer before operation, and technical-specification inoperability of affected and interconnected functions before install. (ch02)
- **SMaintP (software maintenance plan)**: Planning document for repairing nonconforming items and pre-planned actions to maintain performance. Performance improvements and environment adaptations are design changes, not maintenance. (ch02)
- **SMP (software management plan)**: The umbrella planning document: purpose, organization, oversight, responsibilities, risks, and security, including the structural independence and protected budgets of QA, software safety, and V&V from development. (ch02)
- **SOP (software operations plan)**: Planning document for operating the delivered software: start, operate, and stop procedures for all modes with software state consistent with plant mode, backup of data and code, error-message lists with interpretation and resolution steps, and physical, logical, and administrative controls against unauthorized changes. (ch02)
- **SQAP (software quality assurance plan)**: Planning document tying QA procedures to software processes under an NRC-approved QA program, with QA authority and freedom from cost and schedule pressure, and retention of responsibility even when QA work is delegated to a vendor. (ch02)
- **SRP (Standard Review Plan)**: NUREG-0800, the staff's own review guidance. It does not impose new requirements; it tells reviewers what to check. BTP 7-14 sits inside its Chapter 7. (ch01, ch07)
- **SRS (software requirements specification)**: The requirements design output. It must be traceable backward to licensing and design bases and forward to design and V&V, complete (initiation, termination, end state, per-variable accuracy, deterministic multi-mode timing), consistent internally and externally, fully verifiable, modifiable, unambiguous, and baselined under formal change control. (ch03, ch07)
- **SSP (software safety plan)**: Planning document for phase-by-phase software safety analysis, run under a single software safety officer with authority to enforce safety requirements and reject unsafe reused software or tools. (ch02)
- **STM (software training manual)**: Design output scored on process characteristics; understandable to its intended audience and traceable forward from the SRS and training plan. (ch07)
- **STP (software test plan)**: The planning document B.3.1.12 reviews. It spans unit through installation testing, plans retest after failure and the full test set after any modification, and assigns final system testing definition, design, and performance to the V&V group. (ch06)
- **STrngP (software training plan)**: Planning document covering training needs for plant staff, training-effectiveness metrics including end-of-training error rate, and training on a system equivalent to the delivered hardware and software. (ch02)
- **SVVP (software verification and validation plan)**: The planning document B.3.1.10 reviews: the V&V task set, organizational independence, measurement and completion criteria, anomaly handling, and test documentation across unit, integration, validation, installation, and regression levels. (ch05)
- **test case**: Documentation setting the inputs, expected outputs, and acceptance criteria for a test. Functions trace to test cases so every requirement has confirming evidence, and cases stay synchronized with the software design under SCM. (ch05, ch06)
- **test procedure**: Step-level test documentation: setup, inputs, expected outputs, and completion time, whose execution shows results clearly meeting the requirement. It may combine with the test log where each component document keeps its identity. (ch06)
- **thread audit**: The staff's sampling method in B.3.2.2: sample plant parameters, up to about 5 percent of requirements and statistically significant, and trace implementation from purchase specification and functional requirements through code writing and testing. Errors found past claimed V&V are a process alarm. (ch07)
- **unit test**: Testing of individual software units under RG 1.171 / ANSI/IEEE Std 1008-1987. Unit-test documentation meets an eight-item minimum information set, statement coverage alone is not a sufficient completeness criterion, and test products stay under configuration control. (ch06)
- **V&V (verification and validation)**: The process that confirms requirements, design, code, integration, and installation satisfy their requirements and that the software meets the system requirements. RG 1.168 / IEEE Std 1012-2004 sets the method, integrity level 4 sets the task floor, and audits, regression analysis and testing, secure analysis, test evaluation, and user-documentation evaluation join the minimum set. (ch05)
